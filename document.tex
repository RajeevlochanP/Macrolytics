% ==================== 1. OVERVIEW ====================
\section{System Overview}

\begin{introbox}
The Macrolytics backend uses a decoupled, event-driven architecture designed to support
fast deterministic API requests alongside higher-latency asynchronous AI workloads.
Stateless web servers, direct object storage, and queue-backed workers keep request handling
separate from storage and compute-intensive inference.
\end{introbox}

The overall architecture separates the system into four practical concerns: request ingress,
stateless application handling, durable/cache data services, and asynchronous AI processing.
This separation reduces the coupling between user-facing traffic and long-running inference jobs
and provides a clear path to horizontal scaling \cite{xu2020system}.

% ==================== 2. OPTIMIZATIONS ====================
\section{Core Architectural Optimizations}

The following design decisions address the system's principal scalability constraints: large binary uploads,
long-running inference, session state, high-frequency dashboard reads, and transactional persistence.

\subsection{Decoupled Image Processing \& Direct AWS Uploads}
\begin{designbox}{Why this matters}
Routing large image binaries through the Node.js event loop increases memory pressure, while local LLaVA inference
can take 10--30 seconds per request. The web tier should therefore avoid owning either the binary stream or the GPU-bound work.
\end{designbox}

\begin{itemize}
  \item \textbf{Implementation:} The client requests a secure pre-signed URL and uploads the binary directly to AWS S3. S3 triggers an \texttt{ObjectCreated} event to AWS SQS. A background poller on the API reads this event, creates a ``Processing'' database stub, and enqueues a lightweight job reference to BullMQ.
  \item \textbf{Justification:} Storage and compute are completely decoupled from the stateless web tier. Heavy file streaming bypasses the API servers entirely, while GPU-bound inference is safely isolated in background workers \cite{xu2020system}.
\end{itemize}

\subsection{Stateless Web Tier via JOSE \& JWT Context}
\begin{itemize}
  \item \textbf{Challenge:} Binding conversational state to a specific server introduces sticky-session requirements and weakens horizontal scalability.
  \item \textbf{Implementation:} The system uses a $100\%$ stateless web tier. Chat history and operational context are encrypted with JOSE/JWT using \texttt{A256GCM} and returned to the client, which sends the encrypted context on the next request.
  \item \textbf{Justification:} Any API server can handle the next turn without depending on in-memory conversational state \cite{xu2020system}.
\end{itemize}

\subsection{Redis Key Isolation \& Event-Driven Pub/Sub}
\begin{itemize}
  \item \textbf{Key design:} Redis stores focused daily macro aggregates rather than attempting to mirror the entire database. The key format is \texttt{nutrition:daily:\{userId\}:\{dateStr\}}.
  \item \textbf{Atomic operations:} \texttt{hIncrByFloat} updates aggregate values atomically, avoiding repeated SQL aggregation work for dashboard reads.
  \item \textbf{Pub/Sub:} Background workers publish completion events to Redis channels. API servers subscribe and can stream status back to the client through Server-Sent Events (SSE) \cite{xu2020system}.
\end{itemize}

\subsection{SQL vs. NoSQL Database Selection}
\begin{designbox}{Selection}
\textbf{PostgreSQL (Relational SQL)}
\end{designbox}
\begin{itemize}
  \item \textbf{Justification:} Nutrition tracking requires transactional integrity, time-range filtering, pagination, and historical aggregation. PostgreSQL provides the relational structure and ACID guarantees needed for consistent macro tracking \cite{xu2020system}.
\end{itemize}

\subsection{Database Indexing \& Query Optimization}
\begin{itemize}
  \item \textbf{Composite B-Tree Indexing:} To satisfy the assignment's time-range filtering and pagination requirements efficiently, composite indexes (\texttt{user\_id}, \texttt{logged\_at DESC}) were applied to the PostgreSQL schema. This prevents $O(N)$ full-table scans and ensures time-series queries execute in logarithmic time.
\end{itemize}

\begin{designbox}{Architecture at a glance}
\begin{tabularx}{\linewidth}{>{\bfseries\sffamily}p{35mm} Y}
Ingress & HTTPS requests enter through the load balancer; large images bypass the API and upload directly to S3. \\[2pt]
Web tier & API servers remain stateless and delegate long-running AI work to BullMQ. \\[2pt]
Data tier & PostgreSQL is the durable relational store; Redis provides focused aggregates and event fan-out. \\[2pt]
AI tier & Background workers fetch images from S3, run LLaVA inference, and validate structured output before persistence.
\end{tabularx}
\end{designbox}

% ==================== 3. AI ARCHITECTURES ====================
\section{Dual AI Agent Architectures}

The system uses two AI topologies, each optimized for a different operational constraint: low-latency deterministic routing for conversation,
and high-confidence schema validation for asynchronous image understanding.

\subsection{Conversational Chat: Supervisor Multi-Agent Architecture}

Standard ReAct-style loops can overload smaller local models when one prompt must simultaneously manage tone, memory, intent classification,
and strict JSON formatting. The design therefore uses a \textbf{Supervisor Multi-Agent Pattern} \cite{wu2023autogen}.

\begin{itemize}
  \item \textbf{Deterministic routing:} The Supervisor uses \texttt{withStructuredOutput} for intent classification and delegates execution to a specialized sub-agent.
  \item \textbf{Cognitive isolation:} Specialized nodes receive constrained prompts without the full conversational overhead, reducing ambiguity during structured operations \cite{wu2023autogen}.
\end{itemize}

\subsection{Background Vision: Evaluator-Optimizer (Critic) Loop}

Background inference is not limited by interactive response time, so schema correctness becomes the dominant concern. Macro extraction from images therefore uses an \textbf{Evaluator-Optimizer loop} \cite{shinn2023reflexion}.

  \item \textbf{Validation \& retry:} A separate programmatic evaluator checks structural integrity. Invalid output is fed back to the vision model for a targeted retry, helping prevent malformed records from reaching the database \cite{shinn2023reflexion}.
\end{itemize}
